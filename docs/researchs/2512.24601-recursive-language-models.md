# Recursive Language Models (RLMs) and their relation to pydantic-monty

- **Paper:** Recursive Language Models — arXiv:2512.24601 (v3, 2026-05-11)
- **Authors:** Alex L. Zhang, Tim Kraska, Omar Khattab (MIT CSAIL)
- **Code:** https://github.com/alexzhang13/rlm
- **Related project:** https://github.com/pydantic/monty (`pydantic-monty`, tested here at 0.0.21)

## 1. What the paper proposes

RLMs are an inference-time scaffold that lets an LLM process prompts far beyond
its context window (10M+ tokens) by treating the prompt as **data in an external
environment** instead of feeding it into the model:

1. The long prompt `P` is loaded as a **variable inside a persistent Python REPL**.
2. The root LM only ever sees constant-size metadata about it (length, a short
   prefix, how to access it) plus truncated `stdout` from each REPL turn.
3. The LM iteratively **writes code** that peeks into, slices, and transforms
   `P` — and, crucially, the REPL exposes a function for **calling a sub-LM (or
   a full sub-RLM) from inside that code**, so the model can launch
   `Ω(|P|)` or even `Ω(|P|²)` sub-calls programmatically inside loops.
4. The loop ends when the code sets a `Final` variable (so the *output* can also
   exceed the model's window — it is assembled symbolically in the REPL).

Headline results: handles inputs ~100× beyond the context window; on GPT-5 it
beats compaction by 26%, CodeAct by 130%, and Claude Code by 13% (median across
four long-context benchmarks) at comparable cost; a fine-tuned RLM-Qwen3-8B
improves 28.3% over its base model.

The paper's Algorithm 1 vs Algorithm 2 comparison identifies three design
requirements that ordinary tool-calling scaffolds miss:

- **Symbolic handle:** the model must manipulate the prompt *by reference*
  (a REPL variable), never by copying text into its own window.
- **Symbolic output:** the answer is returned from a REPL variable, not
  autoregressively verbalized, so output length is unbounded.
- **Symbolic recursion:** code running *inside the environment* must be able to
  invoke the LM on programmatically constructed inputs — a separate "sub-LLM
  tool" next to a "code tool" is not expressive enough.

## 2. The infrastructure the paper needs — and what monty is

The entire RLM paradigm stands on one component: a **persistent, stateful,
LM-driven Python REPL that can call back into the host (the LM) from inside
executing code**. That is almost a spec sheet for pydantic-monty:

| RLM requirement (paper) | pydantic-monty feature |
|---|---|
| Persistent REPL environment `E`; variables survive across the loop's iterations | `MontySession` — globals/functions persist across `feed_run` calls |
| Prompt loaded "as a variable" without entering the model window | `inputs={'prompt': P}` binds host values as sandbox globals; only what the code prints/returns comes back |
| A `sub_rlm` / `llm_query` function callable *from inside the code*, incl. inside loops (symbolic recursion) | External functions via `external_lookup` — sandboxed code calls a host coroutine that hits the LM (see `snippets/06_llm_agent_in_sandbox.py`) |
| Many sub-calls, ideally concurrent (the paper notes its blocking implementation is a cost/runtime caveat) | `AsyncMonty`: coroutine externals are awaited **concurrently**; `feed_start`/`FutureSnapshot` expose pending calls explicitly |
| `stdout` collected and truncated before reaching the model | `print_callback` / `CollectString(max_bytes=...)` — capped, host-controlled capture |
| The LM writes arbitrary code each iteration — it must not damage the host | Monty's whole premise: Rust interpreter, subprocess workers, no ambient filesystem/network/env; crashes become `MontyCrashedError`, worker replaced |
| Loops over `Ω(|P|)` slices must not run away | `ResourceLimits` (time/memory/recursion) + pool `request_timeout` backstop |
| Long-horizon, many-iteration trajectories (deep research over 10M tokens) | `dump()`/`load_snapshot()`: freeze a *suspended* execution (e.g. parked at a sub-LM call) to bytes and resume later, elsewhere — durability RLM scaffolds built on CPython `exec()` don't have |
| Cheap per-iteration startup (an RLM run is many REPL turns) | Microsecond interpreter startup; warm worker pools; no containers |

The reference RLM implementation uses an ordinary (trusted) Python environment,
which is fine for benchmarks but not for production: the root LM writes
unrestricted code. Monty is the piece that makes the RLM loop *deployable* —
the same interaction pattern with a security and durability story.

There is a real philosophical alignment too: monty's README leads with exactly
the inverted control flow RLMs formalize — instead of "LLM calls tools one at a
time through its context window," the *code* is the agent's control flow and
the LLM/host functions are called from inside it. RLMs are, in effect, the
academic case (with benchmarks) for why that architecture wins on long-context
and information-dense tasks, and monty is purpose-built infrastructure for it.

## 3. Gaps / things monty does not give you for free

- **Python subset.** Monty has no third-party imports, no class inheritance, and
  an incomplete stdlib. RLM trajectories written by frontier models sometimes
  lean on arbitrary libraries; on monty the root model's system prompt must
  constrain it to the subset (as `snippets/07_code_interpreter.py` does), or use
  monty's embedded-CPython worker + `install_dependencies` where trust allows.
- **Truncated-stdout discipline is on you.** The RLM loop appends only metadata
  about stdout to the model history; monty gives you the capture hook
  (`CollectString`) but the truncation/summary policy lives in your scaffold.
- **The outer loop is yours.** Monty is the environment `E`; the RLM driver
  (model ↔ REPL iteration, `Final`-variable convention, recursion-depth
  bookkeeping) is host code you write around it — see the sketch below.

## 4. Sketch: an RLM loop on monty + Ollama

The repo's `snippets/06_llm_agent_in_sandbox.py` is already "depth-0.5": agent
code inside monty calling `call_llm`. A minimal RLM(depth=1) on this stack:

```python
async with AsyncMonty() as pool:
    async with pool.checkout(script_name='rlm.py') as env:   # persistent E
        # 1. load the huge prompt as a variable, never shown to the root LM
        await env.feed_run('pass', inputs={'prompt': huge_prompt})
        history = [system_rlm_prompt, f'len(prompt) = {len(huge_prompt)}']
        while True:
            code = await root_llm(history)                    # LM writes code
            out = CollectString(max_bytes=4096)               # truncate stdout
            try:
                await env.feed_run(
                    code,
                    external_lookup={'llm_query': ollama_query},  # sub-calls
                    print_callback=out,
                )
            except MontyError as e:
                history.append(f'error: {e.display(format="type-msg")}')
                continue
            history.append(f'stdout[:4096]: {out.output}')
            final = await env.feed_run('FINAL if "FINAL" in dir() else None')
            if final is not None:
                break                                          # symbolic output
```

Every box in Algorithm 1 maps onto a monty primitive; `dump()` between
iterations would additionally make the whole RLM run resumable across process
restarts — something the paper's implementation cannot do.

## 5. Takeaway

arXiv:2512.24601 supplies the *evidence* (benchmarks, ablations, cost analysis)
that "LM writes code in a persistent REPL, with LM sub-calls available inside
the code" is the right abstraction for scaling context and reasoning.
pydantic-monty supplies the *runtime* that abstraction needs in production:
sandboxed, resource-limited, stateful, async-recursive, and snapshottable. The
paper describes the algorithm; monty is an industrial-grade implementation of
its environment `E`.
